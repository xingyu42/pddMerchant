# Workbench 商家登录长期存活研究

## Goal

在不读取或保存任何认证实值的前提下，建立官方 Workbench 商家端“30 天内自动登录”的长期观察基线，区分以下三类机制：

1. 本地长期恢复授权在固定期限内可用；
2. 使用或自然运行会延长恢复期限；
3. 短期网页会话失效后，Workbench 仍可用另一份授权恢复新会话。

本任务回答“登录状态为什么能存活、实际存活多久、期限是否会变化”，不以追踪通用网络发送函数或实现 pdd-cli 自动登录为目标。

## Requirements

- 以官方 Workbench 3.7.0.14 的已脱敏静态、动态证据为起点，不把界面文案或 Cookie 属性误写成服务端期限承诺。
- 重建既有 checked 样本的来源和中间运行记录；无法证明的血缘必须标记为 `unknown` 或 `contaminated`，不得补猜。
- 建立按时间排列的观察记录，至少包含样本标签、基线时间、观察时间、样本年龄、进程/窗口状态和结论等级。
- 观察器必须只读，不启动或终止 Workbench，不修改注册表、Profile、Cookie 数据库、认证状态或网络配置。
- 文件观察只能针对命令行显式给出的路径，并且只记录角色标签、是否存在、类型、修改时间和文件大小；不得递归枚举、读取内容或计算内容哈希。
- 不读取或保存 Cookie、token、header、请求实值、响应正文、账号信息、密钥字节、窗口原文、命令行或 Profile 内容。
- 不进行抓包、TLS 解密、进程内存读取、调试器附加或新的业务请求构造。
- checked 与 unchecked、持续运行与长期关闭等对照必须使用独立 Profile；同一账号不能并发多写。
- 结论必须分为 `confirmed`、`disproven`、`unverified`、`risk_hypothesis`，并明确证据覆盖的时间范围。
- 暂停 PddWorkbench.exe 到 `AntCommonInterface::Post` 的通用调用链研究；如未来需要定位恢复协议构造点，另设静态研究任务，且 IDA 只能使用 idalib `force_headless`。
- 本任务不修改生产 `src/`、`bin/` 或现有认证逻辑，不提交、不推送、不归档。

## Acceptance Criteria

- [ ] 形成一份可复核的既有证据台账，逐项标明来源、时间、样本血缘和结论边界。
- [ ] 明确纠正“10 天服务端硬上限”“24-48 小时固定闲置失效”“平台只有 checkLogin + snapshot 一条路线”等未证实表述。
- [ ] 给出 checked 样本从 2026-08-11 原始实验到后续副本的可证明血缘；证据断点不得被算作连续存活时间。
- [ ] 提供一个最小只读观察脚本，并通过 PowerShell 语法检查和非敏感烟测。
- [ ] 观察脚本输出不含输入路径、窗口标题、账号标识、认证值、内容哈希或请求/响应数据。
- [ ] 写清长期观察的检查点、对照组、停止条件和何种证据分别支持绝对期限、滑动续期或长期授权换票。
- [ ] 在没有自然时间序列前，最终结论保持为“已证实恢复路径，期限语义未证实”，不得宣称登录永不过期。

## Notes

- 旧任务 `07-31-daemon-auth-expiry-hardening` 继续负责 pdd-cli 的自然验活、状态快照和失效分类；本任务只研究官方 Workbench 的长期恢复机制。
- “30 天内自动登录”是产品文案，不自动等于绝对 30 天、闲置 30 天或每次使用后续 30 天。
