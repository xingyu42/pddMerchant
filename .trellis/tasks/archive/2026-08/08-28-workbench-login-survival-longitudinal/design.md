# Workbench 商家登录长期存活研究设计

## 1. 研究问题

本任务只回答四个问题：

1. checked 登录产生的官方恢复状态能否跨越短期网页会话寿命继续恢复；
2. 恢复能力从哪个可证明的时间点开始，到哪个观察点仍然有效；
3. 中间启动或自然运行是否会改变后续可恢复期限；
4. 失败时是本地材料缺失、服务端拒绝、网页会话失效，还是仅仅没有观察到足够证据。

## 2. 证据层级

| 等级 | 含义 | 可支持的结论 |
| --- | --- | --- |
| E1 | 代码、资源或界面静态证据 | 存在开关、字段或调用路径，不能证明运行时期限 |
| E2 | 单次脱敏动态状态 | 某一时刻进入登录页或工作台，不能证明长期期限 |
| E3 | 有基线、有血缘的跨时点结果 | 恢复能力至少持续到该时点 |
| E4 | 有对照的期限前后或使用/不使用差异 | 支持绝对期限或滑动续期模型 |
| E5 | 已确认旧网页会话无效，但官方恢复仍建立有效新会话 | 支持长期授权换票模型 |

所有结论同时使用 `confirmed`、`disproven`、`unverified`、`risk_hypothesis` 状态。证据不足时只能降级，不能用模型名称替代事实。

## 3. 样本与血缘

每个 Profile 使用不含账号信息的 `sample_label`。血缘记录只引用脱敏报告或实验标签，不记录 Profile 内容、文件名清单或内容哈希。

血缘状态：

- `verified_copy`：有脚本或脱敏元数据证明从指定父样本复制，且目标在复制前不存在；
- `reused_after_write`：样本已被 Workbench 启动并可能改写，后续只能证明该工作副本的状态；
- `unknown_origin`：没有足够记录证明来源；
- `contaminated`：存在共享写入、人工重新登录或无法排除的覆盖。

连续存活时间只能从可证明的 T0 计算。目录创建时间、复制时间和界面文案都不能代替 T0。

## 4. 观察记录

只读观察器输出 JSON，顶层字段如下：

```text
schema_version
observation_id
sample_label
baseline_utc
observed_at_utc
elapsed_days
duration_seconds
timeline[]
artifact_metadata[]
summary
safety
```

`timeline` 只保存相对毫秒、进程数量、归一化窗口状态集合和是否有响应。窗口状态只允许 `empty`、`login`、`workbench`、`other`，绝不保存窗口原文。

`artifact_metadata` 只处理命令行显式传入的 `role=path` 条目，输出中删除路径，仅保存：

```text
role
exists
kind
last_write_utc
size_bytes
```

观察器不递归遍历目录，不打开文件，不计算哈希，不读取注册表，不读取进程命令行，不启动或停止任何进程。

## 5. 结果解释

观察器只描述可见状态，不自动宣称“自动登录成功”。

- `workbench_reached_without_observed_login`：采样期间到达工作台，且未看到登录窗口；可能遗漏极短窗口，也不能排除采样外人工操作。
- `workbench_reached_after_login_seen`：先看到登录窗口再到工作台；不能仅凭此判断扫码、原生恢复或其他方式。
- `login_only`：只看到登录窗口；表示该次未观察到恢复完成，不等于长期授权永久失效。
- `workbench_only`：观察开始时已经在工作台；只能证明当前状态。
- `no_target_process`：未观察到 Workbench。

协议级结论继续引用已有脱敏报告：checked 重启走 `auto/check/login`，unchecked 重启回到二维码流程。新的观察器不访问网络，也不重复采集 endpoint。

## 6. 对照与检查点

推荐样本组：

| 组 | checked | 使用方式 | 用途 |
| --- | --- | --- | --- |
| A | 是 | 登录后长期关闭，只在检查点启动 | 测绝对/闲置期限 |
| B | 是 | 按固定周期自然启动 | 与 A 比较是否存在使用后续期 |
| C | 否 | 与 A 相同 | 证明恢复来自 checked 路径 |
| D | 是 | 保持自然运行 | 与 A/B 比较运行态是否影响期限 |

同一账号的各组只能串行制作，之后保持单写者；不能让 Workbench、pdd-cli 和 daemon 共享同一 Profile。建议检查点为 T0、24 小时、72 小时、7 天、10 天、14 天、21 天、29 天、31 天和 35 天。每次只做一次自然启动观察，避免为取证制造额外业务活动。

## 7. 判定规则

- 支持“固定绝对期限”：A/B 在相近绝对年龄失效，B 的中间使用没有显著延长。
- 支持“滑动续期”：B 在最后一次自然使用后继续有效，而 A 在相近绝对年龄已失效；至少一次重复对照。
- 支持“运行态续期”：D 明显长于 A，且 B 的结果与使用频率相关。
- 支持“长期授权换票”：先用独立、非侵入证据确认旧网页会话已失效，再观察官方恢复建立有效新会话；不得读取认证值。
- 只支持“重启恢复”：旧会话是否失效未知，但 checked 重启进入业务初始化。

## 8. 停止条件

发生任一情况立即停止该样本观察：需要扫码或输入账号信息、出现风险验证、Profile 被多个进程/工具写入、需要查看认证实值才能继续、观察器输出可能包含敏感数据、系统时间或 Workbench 版本改变、样本血缘断裂。

## 9. 与旧任务的边界

`07-31-daemon-auth-expiry-hardening` 的 `checkLogin + 状态快照 + 失效提醒` 是当前 pdd-cli 安全基线，但不是对官方平台全部恢复能力的断言。本任务不把 Workbench 原生恢复材料移植到 pdd-cli，也不修改 Cookie 期限或伪造活跃行为。
