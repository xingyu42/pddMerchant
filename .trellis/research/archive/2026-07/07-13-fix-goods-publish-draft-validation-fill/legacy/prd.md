# 修复上货草稿校验与字段写入

## Goal

修复 `goods publish --url` 保存草稿后的校验误报，并确保规格、库存与价格要么被可靠写入草稿，要么在保存前明确失败，避免产生“页面已有标题/图片/运费模板却被判空”或“零价、无库存、无规格”的不完整草稿。

## Background

- 2026-07-13 对源商品 `447841256386` 执行仅保存草稿，生成 `goods_commit_id=195935511588`、`goods_id=976822155654`。
- CLI 保存后报 `title_empty`、`no_cost_template`、`no_images`。
- 通过用户真实 Chrome 只读核查同一草稿页，标题有值、轮播图为 8/10、详情图为 9/50、运费模板为“包邮（除偏远地区）”。这证明当前已加载编辑页的状态与“三项全空”冲突，但不能单独证明保存后首次详情查询时的数据状态或响应结构。
- 同一页面的规格/库存/价格确有问题：颜色和尺码没有可靠填入，SKU 库存为空，拼单价与单买价为 0。
- 当前源抓取只提取一个 DOM 最低价和 `skuText`，没有抓取结构化 SKU、逐 SKU 价格或库存；定价层随后只生成统一价格，表单层也没有库存写入逻辑。
- 当前 `fillPrices()` 按全页输入框顺序取前两个 `placeholder*=请输入`，真实页面已有商品货号等更靠前的同类输入框，因此会填错字段。
- 原始上货运行没有保存草稿详情接口的原始响应。原始错误只能证明详情校验拿到了一个非空对象，但在代码直接读取的层级上没有 `goods_name`、`cost_template_id` 和 `gallery`；不能证明该对象为何缺字段。
- 使用真实 `clickSaveDraft()` 做一次性确定性复现：`success=false / result=null` 的业务失败对象会产生原始三项错误；`success=true / result.data={...}` 的嵌套成功对象也会产生完全相同的三项错误；预期的扁平 `result={...}` 才通过。
- 现有 `test/goods-publish.unit.test.js` 共 62 个测试通过，但只覆盖扁平成功响应和真实字段缺失，没有覆盖业务失败对象与嵌套成功响应，因此现有绿灯不能区分上述原因。
- 事后只读手工调用详情接口复现了 `success=false / error_code=2000000 / result=null` 和“网络繁忙，请不要频繁操作”；代码会把这类失败响应继续送入字段校验，能够制造相同三项误报。但多次手工调用本身可能触发频率限制，所以这只是已复现的缺陷路径，不是原始现场证明。
- 能够确认的是“业务失败响应会被错误解释成字段为空”这一代码缺陷；不能确认的是“原始这一次上货就是由该业务失败响应造成”。原始事故根因需要下一次同运行脱敏观测来归类。
- 真实源接口响应为 `encrypt_status=3`，主要数据位于 `encrypt_info`；不得复制旧实现中“统一最低价 + 库存 999”的猜值策略，必须从页面自身解密后的数据边界取得结构化 SKU。

## Requirements

### R0 源商品 SKU 数据必须完整抓取并贯穿上货链路

- 源商品本身存在规格、逐 SKU 价格和库存时，抓取层必须提取结构化 SKU 明细，不能只保留展示文本或区间价。
- 必须定位并修复 `source-scraper -> pricing plan -> form-filler` 之间丢失规格、价格或库存的具体边界。
- 抓取结果必须能区分“真实单 SKU”“真实多 SKU”和“因反爬/字段漂移导致 SKU 明细缺失”，不得把第三种情况降级成单 SKU。
- 源端 SKU 明细不完整时，应在创建商家草稿前明确失败，不能使用统一价格、猜测库存或零值继续。

### R1 草稿详情校验必须读取真实响应结构

- 下一次真实草稿验证前必须先增加脱敏观测点，在同一次运行中记录详情响应的业务状态、结果类型和字段键名；不得记录原始响应内容。
- 对草稿详情接口响应做显式、可测试的规范化，再校验标题、运费模板和轮播图。
- 兼容当前已知的字段命名/嵌套差异，但不得用页面可见文本掩盖接口数据缺失。
- 业务失败、`result=null` 或瞬时不可用必须返回独立的 `draft_verification_unavailable` warning，不能转成字段缺失，也不能绕过保存请求体严格校验。
- 保留严格校验：真实缺失或运费模板不一致时仍阻止继续提交发布。
- 错误详情继续只输出问题代码和非敏感标识，不泄露商品图片 URL、Cookie 或原始响应。

### R2 规格、库存和价格必须安全写入

- 单 SKU 商品必须写入有效库存、拼单价、单买价和参考价，并在保存后校验非空且大于 0。
- 多 SKU 商品必须按规格值而不是表格索引匹配 SKU 行；规格组合、价格、库存来源不足时不得猜值。
- 无法建立可靠映射时，应在保存草稿前返回明确的 `E_BUSINESS`，不得生成新的不完整草稿。
- DOM 填写必须触发商家后台框架需要的状态更新，不能只修改表面 `input.value`。

### R3 保持发布安全边界

- 默认命令仍只保存草稿；只有 `--confirm` 才允许进入提交发布阶段。
- 任一严格校验失败都不得调用提交接口。
- 不自动删除或修改本次已存在的草稿 `195935511588`。

### R4 范围控制

- 本任务只覆盖草稿校验与规格/库存/价格写入。
- 商品属性填写率、详情装修增强、标题改写策略和正式发布流程优化不在本任务范围内，除非它们被证明是完成上述验收的直接阻塞项。

## Acceptance Criteria

- [ ] 草稿详情规范化测试覆盖真实嵌套响应，标题、运费模板和图片存在时不再产生 `title_empty`、`no_cost_template`、`no_images`。
- [ ] 在下一次真实写入前完成脱敏观测，确认原始误报属于业务失败、响应嵌套漂移、保存后竞态或其他哪一种路径；未确认前不把任一假设写成唯一根因。
- [ ] 对标题、运费模板或图片真实缺失及模板 ID 不一致的场景，严格校验仍返回对应问题代码。
- [ ] 对真实多 SKU 源商品，抓取结果包含可按规格值匹配的逐 SKU 价格与库存；字段缺失/脱敏时在创建商家草稿前失败。
- [ ] 单 SKU 表单测试证明库存、拼单价、单买价和参考价写入有效值并触发框架状态更新。
- [ ] 多 SKU 流程仅在规格行可可靠匹配时填写；缺少逐 SKU 数据时在创建/保存不完整草稿前失败。
- [ ] 保存请求放行前的严格校验覆盖：标题、轮播图、运费模板、规格组合数量、库存和价格均有效；平台保存响应也必须成功。
- [ ] 草稿详情查询业务失败时只产生 `draft_verification_unavailable` warning；查询成功且确认字段缺失时仍阻止后续提交。
- [ ] 默认草稿模式和 `--confirm` 提交边界保持不变，相关回归测试通过。
- [ ] 运行 `test/goods-publish.unit.test.js`、相关 PBT/E2E 以及受影响的共享测试；最终核对 `git diff` 仅包含本任务范围。

## Product Decision

- 上架所需的规格、逐 SKU 价格和库存应当来自源商品抓取。不得把抓取失败当成源商品没有数据，也不提供统一价格/库存猜测回退；应先修复抓取链路，仍不完整时在创建商家草稿前失败。
- 目标草稿每个 SKU 的拼单价和单买价必须分别原样使用源商品的 `groupPrice` 与 `normalPrice`；原始“元”价格只做精确分值归一化，不再对这两个售价应用加价倍率。
- 目标草稿参考价必须原样使用源商品顶层 `linePrice`，经精确分值归一化后贯穿为 `sourceReferencePriceCents`；不得使用 SKU 的 `marketPrice`，也不得用拼单价乘 `1.8` 回退。参考价缺失、非正数或不严格高于所有单买价时，必须在创建草稿前失败。
