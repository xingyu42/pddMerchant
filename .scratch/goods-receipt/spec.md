# PRD：商品预估实收查看（`pdd goods receipt`）

Status: ready-for-agent

## Problem Statement

商家在拼多多后台「商品价格管理」页面能看到每个规格的预估实收，也就是叠加商家出资优惠后实际能收到多少钱。现在要看这个数只能逐页打开网页：每个商品默认只展示 2 个规格，剩下的规格要一个个展开；单件和多件两种实收要靠页面开关来回切；商家出资口径也要在弹窗里切换。pdd-cli 已经覆盖了商品列表、改价和利润报表，但没有渠道读取这个平台给出的数字，商家无法在命令行或自动化流程里批量核对「当前价格下，每个规格能实收多少」。

## Solution

新增只读命令 `pdd goods receipt`，按 SKU 原样报告平台给出的 **Estimated Merchant Receipt（预估实收）**：

- 预估实收 = 券前价 − 商家出资优惠，数值由拼多多计算，CLI 原样报告，不自己重算。
- 每个 SKU 同时给出单件预估实收，以及多件最低预估实收（附带对应的件数）。
- 每个场景都列出商家出资优惠的金额和明细。
- 自动补全每个商品的全部 SKU。
- 默认使用「商家出资常规优惠」口径，可切换到「商家出资所有优惠」口径；输出会标明当前口径，两种口径的数值不会混在一起。
- 支持按商品 ID 筛选，并按上游的分页规则查询（每页最多 10 个商品）。

## User Stories

1. 作为商家，我想用一条命令列出全店商品各个 SKU 的预估实收，这样不用逐页打开后台。
2. 作为商家，我想按一个或多个商品 ID 查询预估实收，这样能快速核对刚调过价的商品。
3. 作为商家，我想用重复的 `--goods-id` 参数或逗号分隔传入多个商品 ID，这样脚本拼参数更方便。
4. 作为商家，我想看到每个商品的全部 SKU，而不是后台默认展示的前 2 个，这样不会把部分规格误当成全部规格。
5. 作为商家，我想看到每个商品的 SKU 总数，这样能确认输出的规格是完整的。
6. 作为商家，我想看到每个 SKU 的券前价，这样能知道预估实收是从哪个价格算起的。
7. 作为商家，我想知道券前价来自拼单价还是某个活动价（比如「限量折扣」），这样能理解为什么券前价和拼单价不一样。
8. 作为商家，我想同时看到拼单价，这样有活动价时也能对照原始拼单价。
9. 作为商家，我想看到单件购买时的商家出资优惠金额和预估实收，这样知道卖一件能收多少。
10. 作为商家，我想看到多件购买时平均单件的预估实收最低是多少、在买几件时出现，这样能评估满减、多件折扣让我最多少收多少。
11. 作为商家，我想看到多件场景下平均每件的商家出资优惠，这样能对比单件和多件的让利差异。
12. 作为商家，我想看到每个场景各自生效的商家出资优惠明细（优惠名称、文案、金额），这样能知道是哪项优惠拉低了实收。
13. 作为商家，我想看到多件场景下各项优惠的合计金额，这样能和后台「买 N 件合计减 X 元」对上。
14. 作为商家，我想在没有任何商家出资优惠时看到优惠为 0、明细为空，这样能和「平台没给数据」区分开。
15. 作为商家，我想在平台没给多件场景时看到多件结果为空值，而不是 0，这样不会误以为多件实收为 0。
16. 作为商家，我想在单件场景缺失时收到明确的警告，这样知道这条数据不完整。
17. 作为商家，我想切换到「商家出资所有优惠」口径（包含非公开优惠、多单立减、商家出资平台券），这样能看到最保守的实收估计。
18. 作为商家，我想在每次输出里看到当前口径，这样不会把两种口径的数字混着比较。
19. 作为商家，我想默认口径和后台页面的默认口径一致（常规优惠），这样命令行和网页看到的默认结果一致。
20. 作为商家，我想用 `--page`、`--size` 翻页，这样能分批读取全店商品。
21. 作为商家，我想在 `--size` 超过 10 时立即收到用法错误，这样不会在上游报错后才发现。
22. 作为商家，我想在店铺没有开放商品价格管理或上游拒绝查询时收到业务错误和上游原始提示，这样知道问题出在平台侧。
23. 作为商家，我想看到返回的商品总数，这样知道一共要翻几页。
24. 作为商家，我想看到一段中文事实摘要（商品数、SKU 数、口径），这样在终端里一眼看清结果范围。
25. 作为自动化脚本作者，我想用 `--json` 得到单行 v2 envelope，这样能稳定地被程序解析。
26. 作为自动化脚本作者，我想所有金额都是以元为单位的 `_yuan` 字段，这样不用自己处理分和元的换算。
27. 作为自动化脚本作者，我想用 `--all-accounts` 对多个店铺批量查询，这样能统一核对旗下所有店铺。
28. 作为注重隐私的使用者，我想输出里不含商品图片链接和上游原始对象，这样输出可以安全地分享和留档。
29. 作为维护者，我想在平台返回了不属于当前口径的场景数据时，这些数据被忽略并记一条警告，这样口径不会被意外污染。

## Implementation Decisions

**领域与口径**
- 使用 `GLOSSARY.md` 中的术语 **Estimated Merchant Receipt（预估实收）**，它属于平台报告的事实。CLI 不用价格或费率重算，也不推导技术服务费、平台补贴（上游没有这些字段）。
- 两种商家出资口径通过请求里的场景值区分，服务端不保存口径偏好：
  - 常规优惠：单件场景 7，多件最低场景 8
  - 所有优惠：单件场景 10，多件最低场景 11
- 场景 9（未来走势）这次不用。

**命令接口**
- `pdd goods receipt [--goods-id <id>...] [--page <n>] [--size <n>] [--caliber regular|all]`
- `--size` 默认 10，取值 1–10，超出时报 `E_USAGE`，退出码 2。
- `--caliber` 默认 `regular`，其他值报 `E_USAGE`，退出码 2。
- 只按商品 ID 筛选，不支持按商品名称或类目筛选，也不支持排序。
- 只读命令，支持 `--all-accounts`。
- CLI 不自动翻页拉取全店，每次只取一页。

**上游接口（商品价格管理页面的 madrid 接口，POST JSON，通过共享 endpoint client 和浏览器页面会话发起）**
- 列表接口 `price_manage/query_goods_price_with_page`
  - 请求字段：`page_num`、`page_size`、可选的 `goods_search_condition.goods_id_list`、当前口径的 `consult_price_scene_list`，以及固定值 `source_type: "PriceManagent"`（这是上游原样拼写）。
  - 每页最多 10 个商品（上游错误码 40003）；每个商品只带回 2 个 SKU，剩余数量在 `remain_sku_num` 里。
- 补全接口 `price_manage/expand_all_sku`
  - 只对 `remain_sku_num > 0` 的商品按顺序调用。
  - 请求字段：`goods_id`、当前口径的场景值、`exposed_sku_id_list`（列表接口已经返回的 SKU ID）。
  - 返回其余 SKU，结构和列表接口里的 SKU 相同。
- 上游金额单位都是分（整数），在视图层统一转成元。

**数据结构（data 契约 v2）**
- 顶层字段：`headline`、`items`、`total`、`page`、`size`、`caliber`（中文标签：「商家出资常规优惠」或「商家出资所有优惠」）。
- 商品级字段：`goods_id`、`goods_name`、`sku_count`、`skus[]`。
- SKU 级字段与上游映射：

  | 输出字段 | 上游来源 |
  |---|---|
  | `sku_id` | `sku_id` |
  | `spec` | `sku_spec` |
  | `group_price_yuan` | `group_price` |
  | `pre_coupon_price_yuan` | 有 `activity_price_info.activity_price` 时取它，否则取 `group_price` |
  | `pre_coupon_price_source` | 有活动价时取 `activity_type_desc`，否则为「拼单价」 |
  | `single.merchant_discount_yuan` | 单件场景的 `avg_discount_amount` |
  | `single.receipt_yuan` | 单件场景的 `promo_price_list[0]` |
  | `single.discounts[]` | 单件场景的 `merge_promo_detail_list[]` → `{ name ← source_type_str, desc ← promo_desc, discount_yuan ← discount_amount }` |
  | `multi.quantity` | 多件场景的 `number` |
  | `multi.avg_merchant_discount_yuan` | 多件场景的 `avg_discount_amount` |
  | `multi.receipt_yuan` | 多件场景的 `promo_price_list[0]` |
  | `multi.discounts[]` | 多件场景的 `merge_promo_detail_list[]`，`discount_yuan` 是多件合计 |

- 零值与空值规则：
  - 平台明确给出的无优惠：优惠金额为 `0`，`discounts` 为 `[]`。
  - 缺少多件场景：`multi` 为 `null`。
  - 缺少单件场景：`single` 为 `null`，并在 `meta.warnings` 记录一条警告。
  - 场景值不属于当前口径的数据一律忽略，并在 `meta.warnings` 记录一条警告。
- 不输出以下内容：`thumb_url` 等图片、30 日销量、红线价和低价预警、全站营销 `effect_promotion`、上游原始对象。
- headline 只陈述事实（商品数、SKU 数、口径），不给经营建议，不打分。

**错误处理**
- 上游业务错误（包括店铺不在价格管理灰度名单）映射为 `E_BUSINESS`，退出码 6，提示文案保留上游原文。
- 查询前不调用灰度或白名单接口做预检查。目前没有「不在名单里」的真实响应样本，等拿到样本再考虑加预检查。

**模块划分**（遵循 commands → services → adapter → infra）
- adapter：新增两个 endpoint spec（列表、补全），只负责请求参数和响应形状校验，fixture 名称和 `spec.name` 保持一致。
- services：新增预估实收服务，负责调用列表接口、按顺序补全 SKU、按口径筛选场景、收集警告。
- services/views：新增预估实收视图，负责按白名单投影字段、分转元、生成中文标签和 headline。
- commands：新增 `goods receipt` 命令文件，在 goods 的注册器里注册，命令本身保持薄层。
- fixture 传输层：endpoint spec 新增一个可选的 fixture 变体键（例如按 `goods_id`），加载顺序为 `<spec.name>.<变体>.json`，缺失时回退到 `<spec.name>.json`。未声明这个键的现有 spec 行为不变。

## Testing Decisions

- 好的测试只验证外部行为：CLI 退出码、envelope 的 `data`、`meta.warnings`、`error.code`，不断言内部函数调用和中间结构。
- **主接缝：CLI e2e 测试**（起子进程，使用 fixture 适配器）。要覆盖的情况：
  - 全店分页查询，`total`、`page`、`size` 正确。
  - `remain_sku_num > 0` 的商品补全出全部 SKU，`sku_count` 正确；不同商品通过 fixture 变体返回不同的补全结果。
  - 分转元正确；券前价分别来自拼单价和活动价两种情况。
  - 单件、多件的优惠和明细输出正确，多件明细是合计金额。
  - 无优惠时为 0 和空数组；缺少多件场景时 `multi` 为 null；缺少单件场景时有警告。
  - `--caliber all` 请求和采用的场景值是 10、11；混入其他口径的场景值时被忽略并有警告。
  - `--goods-id` 支持重复传和逗号分隔。
  - `--size 11` 或非法 `--caliber` 返回退出码 2。
  - 上游业务错误返回退出码 6，并保留上游提示。
  - 输出里不含图片链接、`http` 字符串和上游私有字段。
- **契约接缝：`data-contract-v2`**：在 `V2_CASES` 里加入 `goods.receipt`，带上商品级和 SKU 级的 `entityFields`。
- **fixture 变体键**：在现有 fixture transport 测试里补一个用例，验证有变体文件时加载变体、缺失时回退到基础文件，以及未声明变体键的 spec 行为不变。
- 测试数据使用合成的脱敏 fixture，结构参照抓包样本；真实店铺样本不进仓库。
- 可参考的先例：`goods traffic` 的 e2e 测试和测试数据工厂、`data-contract-v2` 的 `V2_CASES`、fixture transport 测试。
- 只跑 fixture 模式的自动化测试。要不要用真实账号验证，另外向用户确认。

## Out of Scope

- 未来价格走势（场景 9 和走势查询接口）。
- 「所有优惠」口径下的优惠详情和优惠记录接口。
- 红线价、低价预警，以及「仅看红线品」「仅看低价风险品」筛选。
- 全站营销 `effect_promotion`。
- 按商品名称、类目筛选和排序。
- CLI 内部自动翻页拉取全店。
- 查询前的灰度或白名单预检查。
- 把预估实收接入 `goods profit`；ADR 0004 的收入口径保持不变。
- 一切改价和优惠设置的写操作（改价继续走 `goods update price`）。

## Further Notes

- 抓包时本店只有全店满减一种商家优惠，所以以下两点还没在真实数据上验证：多种优惠叠加时 `merge_promo_detail_list` 的样子，以及两种口径数值不同的情况。fixture 要人为构造这两种情况。
- 抓包时不带 Anti-Content 重放查询也成功了，但这只是当时的表现。实现时仍然通过浏览器页面会话发起请求，和其他 endpoint 一致。
- 上游场景描述里有原文错别字（例如「多件件」），输出不透传场景描述，所以不受影响。
- 「所有优惠」口径包含的内容以后台弹窗文案为准：商家出资常规优惠、商家出资非公开优惠、多单立减、商家出资平台券。
