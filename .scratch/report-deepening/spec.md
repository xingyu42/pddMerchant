# PRD：现有报表加深（`diagnose customer-service` 销售数据、`diagnose reviews` 商品评分）

Status: ready-for-agent

来源：2026-11-19 设计访谈（店透视接口使用率盘点后的四个缺口之一）。实测依据见 `docs/research/cs-sales-and-goods-evaluate-recon-2026-11-19.md`。

## Problem Statement

商家用 `diagnose customer-service` 能看到咨询人数、回复率和响应时长，却看不到这些咨询带来了多少成交：多少人询单、多少人最终成团、询单转化率多少、客服带来的销售额多少。这些数字在商家后台「多多客服-销售数据」页面上有，CLI 没有输出。

商家用 `diagnose reviews` 能看到中差评、不满意标签和问题类型，却看不到每个商品的评价总体水平：近 30 日有多少条有效评价、描述 / 物流 / 服务三项平均分是多少。只看中差评条数，分不清「评价很多、差评占比很低」和「评价很少、差评占比很高」的商品。

## Solution

两个命令都保持原有选项和原有输出，各自在 `data` 中增加一个区块，命令数量不变。

- `diagnose customer-service` 增加 `sales` 区块：平台「多多客服-销售数据」口径下的询单人数、成团人数、询单转化率（Inquiry Conversion）、客服销售额（Customer-Service Sales），含区间汇总和逐日趋势；逐日趋势另带询单转化率的同类目前 10% 均值和整体均值。区块带自己的口径标签和日期窗口，窗口结束于今天往前第 3 天，因为平台只提供 3 天之前的销售数据。
- `diagnose reviews` 增加 `goods_scores` 区块：平台「数据中心-评价数据」口径下，按商品列出近 30 日有效评价数和描述 / 物流 / 服务三项平均分。区块固定为近 30 日，带自己的口径标签和窗口天数，在任何 `--days` 下都输出。

两个区块拉取失败时各自为 `null` 并给出提示，原有数据照常输出，退出码不变。

## User Stories

1. 作为商家，我想在客服报告里看到询单人数，以便知道有多少咨询者进入了购买考虑。
2. 作为商家，我想看到询单后的成团人数，以便知道客服接待带来了多少成交买家。
3. 作为商家，我想看到询单转化率，以便了解咨询到成交的比例。
4. 作为商家，我想看到客服销售额，以便知道客服接待对应的成交金额。
5. 作为商家，我想看到询单转化率的同类目前 10% 均值和整体均值，以便把自己的数字放到同类目里看。
6. 作为商家，我想看到销售数据的逐日趋势，以便发现哪几天询单多而成团少。
7. 作为商家，我希望销售数据标出自己的日期区间，以便知道它比咨询数据早结束两天。
8. 作为商家，我希望销售数据标出口径「多多客服-销售数据」，以便和客服数据口径、数据中心口径区分开。
9. 作为商家，我希望 headline 里有一行带日期区间的销售数据概括，以便不展开明细也能读到结论。
10. 作为商家，我希望某天没有询单时转化率显示为 `null`，以便区分「没有询单」和「转化率为 0」。
11. 作为商家，我希望成团 0 人时客服销售额按平台原值显示为 `null`，以便输出和后台一致。
12. 作为商家，我希望销售数据拉取失败时仍能拿到咨询和回复率数据，以便一处失败不影响整份报告。
13. 作为商家，我希望销售逐日趋势单独失败时仍能拿到销售区间汇总，以便保留已取到的部分。
14. 作为商家，我希望 `--days` 同时决定咨询窗口和销售窗口的长度，以便只用一个选项。
15. 作为商家，我想在评价报告里看到每个商品近 30 日的有效评价数，以便知道中差评条数的分母大致有多大。
16. 作为商家，我想看到每个商品的描述平均分，以便比较不同商品的评价水平。
17. 作为商家，我想看到每个商品的物流平均分和服务平均分，以便区分问题出在商品、物流还是服务。
18. 作为商家，我希望近 30 日没有评价的商品三项平均分显示为 `null`，以便不把「没有评价」读成「0 分」。
19. 作为商家，我希望商品评分区块写明「近 30 日」和口径「数据中心-评价数据」，以便在 `--days 180` 时不把它当成 180 天的数据。
20. 作为商家，我希望商品评分带商品名，以便不用再查商品 ID 对应哪个商品。
21. 作为商家，我希望 headline 里有一行「近 30 日有效评价商品 N 个」，以便快速知道有多少商品在产生评价。
22. 作为商家，我希望商品很多、列表被截断时看到明确提示，以便知道结果只是一部分。
23. 作为商家，我希望商品评分拉取失败时仍能拿到中差评、标签和问题类型，以便一处失败不影响整份报告。
24. 作为商家，我希望用 `--json` 把两个新区块交给脚本或 LLM，以便自动汇总。
25. 作为商家，我希望报告只陈述平台给出的数字，以便自己判断，不被 CLI 的推算影响。
26. 作为维护者，我希望两个区块各自失败、各自降级，以便沿用现有报表的可选数据写法。
27. 作为维护者，我希望未确认含义的上游字段留在视图白名单之外，以便输出里每个字段都有依据。
28. 作为维护者，我希望契约测试覆盖两个新区块的字段集，以便以后改动时字段不会悄悄增减。

## Implementation Decisions

### 共同约定

- 不新增命令，不新增选项；两个命令的现有字段、headline 现有行、`hints` 现有文案保持原样。
- 两个新区块都作为报表的可选数据：普通的上游错误降级为 `null` 加一条 hint，命令仍成功、退出码不变；整条命令超时、程序内部错误和中止照旧让命令失败。
- 新区块各自带 `caliber`。不同口径的值各自陈述，不相加、不对账、不拼成一条序列（见术语表 Reply-Rate Caliber、Inquiry Conversion、Customer-Service Sales）。
- 单位按 data 契约 v2：比率由上游 0–1 换算为 0–100，字段以 `_pct` 结尾；金额为元，以 `_yuan` 结尾；缺失为 `null`。
- 上游字段经白名单投影；下文未列出的上游字段都不进入 `data`。
- 新端点规格沿用同领域现有端点的导航、成功判定和错误映射写法；fixture 以端点规格名为键，用测试数据工厂构造合成数据。

### `diagnose customer-service` 的 `sales` 区块

- 形状：

  | 位置 | 字段 |
  | --- | --- |
  | `sales` | `caliber`（固定「多多客服-销售数据」）、`window`（`start_date`、`end_date`、`days`）、`summary`、`trend` |
  | `sales.summary` | `inquiry_user_count`、`group_user_count`、`inquiry_conversion_rate_pct`、`cs_sales_amount_yuan` |
  | `sales.trend.items[]` | `date`、上面四项、`category_top10_avg_inquiry_conversion_rate_pct`、`category_avg_inquiry_conversion_rate_pct` |

- 窗口：天数沿用 `--days`（1–63，默认 30），结束日为上海时区今天往前第 3 天，起始日按天数向前推。现有 `window`、`summary`、`trend` 仍截至昨天。
- 区间汇总取平台的区间汇总接口（请求体为起止日期），CLI 不自行由逐日数据相加。
- 逐日趋势取平台的逐日接口。该接口没有参数，固定返回约 31 天，由点击「销售数据」页签触发，实现时用现有的「触发后抓包」取法；按销售窗口过滤后按日期升序输出。`--days` 大于 31 时趋势只覆盖平台返回的那部分日期，与现有 `trend` 的做法一致。
- 同类目前 10% 均值和整体均值只在逐日数据里有，所以只出现在 `sales.trend.items[]`。
- 空值按上游原值：询单 0 人时转化率为 `null`；成团 0 人时客服销售额为 `null`；尚未出数的日期整行为 `null` 并保留在趋势里，不另加提示。
- 不输出：客服可提升销售额（平台推算的潜力值）、各项环比字段。
- headline 在现有行之后增加一行，写明销售窗口的日期区间，例如「2026-11-10 至 2026-11-16 询单 12 人，成团 6 人，询单转化率 50%，客服销售额 153.67 元」；值为 `null` 的部分略去；询单人数为 `null` 时写「<区间> 无询单数据」；`sales` 为 `null` 时不加这一行。
- 失败粒度：区间汇总失败时 `sales` 整块为 `null`，hint「客服销售数据拉取失败」；区间汇总成功而逐日失败时只有 `sales.trend` 为 `null`，hint「客服销售逐日趋势拉取失败」。
- 窗口起始日与平台保留范围：实测 63 天及更长的区间请求都不报错，早于今天往前 63 天的数据是否保留未确认。先按上述窗口实现；真实账号验证时查看页面自定义日期的最早可选日，若它晚于窗口起始日，再把 `sales.window` 的起始日收到那一天并如实标出 `days`。

### `diagnose reviews` 的 `goods_scores` 区块

- 形状：

  | 位置 | 字段 |
  | --- | --- |
  | `goods_scores` | `caliber`（固定「数据中心-评价数据」）、`window_days`（固定 30）、`items`、`total`、`truncated` |
  | `goods_scores.items[]` | `goods_id`（字符串）、`goods_name`、`review_count`、`desc_score_avg`、`logistics_score_avg`、`service_score_avg` |

- 数据来自数据中心评价数据页的「近 30 日存在有效评价的商品」列表接口，明文。`review_count` 是近 30 日有效评价数；三项平均分保留 2 位小数。
- 近 30 日有效评价数为 0 的商品也在列表里，上游三项平均分为 0，输出为 `null`。
- 在任何 `--days` 下都输出，内容始终是近 30 日；与 `negative_reviews.total` 各自陈述。
- 分页：每页 10 条（唯一实测通过的值，50 和 100 被上游拒绝），最多取 20 页即 200 个商品，排序用页面默认值。`total` 取首页返回的商品总数（越过末页时上游总数回落为 0，与评价列表同样处理）。取满 20 页仍有剩余时 `truncated` 为 `true` 并加 hint「商品评分列表已达 200 个商品上限，结果已截断」。
- 不输出：今日评价数（属于今日实时，归 `realtime-data`）、三个排名字段、`starless4OrdrDfltRevCnt1m`、`avgUapplDescRevScr1m`、`avgAntiDescCtgrpRevScrPct1m`、商品图片、商品状态。
- headline 在现有行之后增加一行「近 30 日有效评价商品 N 个」，N 为 `review_count` 大于 0 的商品数；`goods_scores` 为 `null` 时不加这一行。
- 失败时 `goods_scores` 为 `null`，hint「商品评分拉取失败」。命令整体是否失败仍只由原有三项数据（标签聚合、问题类型、中差评列表）决定，沿用现状。

### 文档与契约

- 命令说明（`skills/pdd-cli` 的报表文档）、CHANGELOG、`.trellis/spec` 中的服务契约和命令契约同步写入两个新区块。
- 术语表已收录 Inquiry Conversion 和 Customer-Service Sales，实现与文档沿用这两个术语。

## Testing Decisions

- 好的测试只断言外部行为：CLI 在 fixture adapter 下输出的 envelope `data`，以及服务函数在给定时钟和端点返回下的结果；不断言视图内部如何取值。
- 只用两个现有接缝，不新增。
- **主接缝：CLI 加 fixture adapter。** 用 `runCli` 跑两个命令，断言：
  - 新区块的字段、单位换算、口径标签和 headline 新增行；
  - 区块失败时为 `null` 并带对应 hint，退出码仍为 0，原有数据不受影响；
  - 未输出的上游字段确实不出现；
  - `data-contract-v2` 中两个命令的 case 扩到新区块的字段集。
- **辅接缝：服务层加假时钟。** CLI 接缝是子进程，时间冻结不了，与日期和分页有关的行为放在这里：
  - 销售窗口结束于今天往前第 3 天，起始日随 `--days` 变化，跨月和闰日用日历运算；
  - 逐日趋势按销售窗口过滤；
  - 商品评分翻页、总数取首页、取满 20 页时标记截断。
- fixture 一律用合成数据，形状照实测响应（含询单 0 人、成团 0 人、尚未出数、评价数 0 四种空值形态），避免测试通过而真实账号取不到数据。
- Prior art：`test/e2e/customer-service.e2e.test.js`、`test/e2e/reviews.e2e.test.js`（runCli + fixture、可选数据失败降级）、`test/services/customer-service.test.js`、`test/services/reviews.test.js`（假时钟、替换端点调用、分页）、`test/contract/data-contract-v2.test.js`。
- 测试覆盖范围之外：销售逐日趋势靠点击「销售数据」页签触发，fixture 模式不经过真实页面，这一步在真实账号验证时确认。

## Out of Scope

- `goods reviews`：本次不动。
- 今日实时数据（今日评价数、今日销售额与成团人数、分时咨询）：归 `.scratch/realtime-data/`。
- 省级地域报告：见 `.scratch/region-report/`。
- 字体混淆指标解码：见 `.scratch/spider-font-decoding/`。
- `diagnose reviews` 标签聚合在真实账号上失败的缺陷：见 `.scratch/diagnose-reviews-keywords/`。
- 数据中心口径的客服接口（服务质量、服务趋势）和客服绩效明细（含客服账号名）。
- 商品评价分排名、店铺评价分排名、店铺级 DSR 趋势。
- 按商品 ID 查询商品评分、自定义排序。
- 客服可提升销售额，以及任何由 CLI 推算的评分、建议或对比结论。

## Further Notes

- 实测环境只有一个店铺，量小：商品 2 个，近一年评价 127 条，销售数据逐日多为个位数。以下几项仍未验证，都不挡实现，留到真实账号验证时观察：
  - 商品评分每页 20 / 30 / 40 条是否可用；
  - 按商品 ID 查询、排序参数的含义；
  - 早于今天往前 63 天的销售数据是否保留；
  - 物流、服务两项平均分的含义只有上游字段名作依据（实测商品三项相等，无法单独核对）；
  - 三个排名字段在有排名的店铺上的取值。
- 区间汇总在实测的三个区间上都等于逐日相加，未观察到跨日去重；实现仍以平台的区间汇总为准。
- 真实账号验证需要先重新登录：侦察之后保存的登录态已失效（`pdd doctor` 返回 `E_AUTH_EXPIRED`）。验证时输出只看条数、区间和字段名，不记录评价正文、订单号和店铺 ID。
