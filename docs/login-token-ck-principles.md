# LoginToken 获取与 ck 更新：原理及跨项目接入规范

文档版本：1.1  
更新日期：2026-10-04  
面向读者：需要在自己的项目中获取登录凭据、检查登录状态和替换 Cookie 的开发者。

本文可独立阅读，不要求访问原工程、逆向记录或其他项目文档。正文分为已核对的凭据机制和接入设计规范；设计中的步骤、字段和状态用于指导实现，不代表某个软件包已经提供同名接口。示例中的凭据均为演示值。

## 1. 目标与整体原理

目标是：**通过正常授权获得 LoginToken 和配套 Cookie，检查可用性，再更新业务项目中对应账号的 ck。**

这里的 ck 是 HTTP 请求头 `Cookie` 的内容。例如：

```http
Cookie: PASS_ID=demo_token; auxiliary=demo_value
```

整个过程分为五步：

1. 建立登录会话：复用经授权保存的会话，或让用户完成一次正常登录。
2. 取得候选凭据：从该会话读取目标地址适用的 Cookie，提取其中的 `PASS_ID`。
3. 检查登录状态：用本次候选 ck 发起独立 HTTP 请求，明确确认登录有效。
4. 核对账号与业务权限：确认登录的是预期账号，并能执行目标项目需要的只读业务。
5. 提交更新：把同一次获取的凭据作为一个整体，替换该账号的旧记录。

**取得凭据、检查凭据、保存凭据是三件不同的事。** 本地改写字符串或重新保存 ck 不会自行改变服务端会话；检查成功也不等于为账号增加了业务权限。

本文把“更新 ck”定义为调用项目替换本地使用的登录材料，不把它称为服务端续期。需要重新建立会话时，走正常登录授权流程。

## 2. 数据名称与表示方式

### 2.1 关键术语

| 名称 | 含义 | 使用要求 |
| --- | --- | --- |
| `LoginToken` | 应用层传递登录凭据的字段名 | 先识别来源格式，不能只凭字段名决定怎样发送 |
| `PASS_ID` | 一项具体的 Cookie 名称 | 名称区分大小写、精确匹配，值原样保留 |
| `pass_id_value` | `PASS_ID` 等号后面的值 | 不包含 `PASS_ID=` 前缀，不包含 Cookie 属性 |
| `login_token` | 本文浏览器接入设计中的规范化表示 | 使用完整的 `PASS_ID=值`，不是裸值 |
| `ck` | 对一个目标 URL 发送的 Cookie 请求头内容 | 使用多个 `名称=值`，以 `; ` 连接，不带 `Cookie:` 前缀 |
| 结构化 Cookie | 包含名称、值、域、路径、过期等字段的记录 | 用于保存来源信息和为不同 URL 选择 Cookie |
| 浏览器上下文 | 一个相互隔离的浏览器会话容器 | 不同账号、不同获取任务分别管理 |

本文的下划线写法 `login_token` 是接入字段约定；驼峰写法 `LoginToken` 用于讨论原应用的凭据字段。二者不能脱离来源格式直接互换。

### 2.2 响应 Cookie 与请求 Cookie

服务器通过响应头设置 Cookie：

```http
Set-Cookie: PASS_ID=demo_token; Path=/; Secure; HttpOnly
Set-Cookie: auxiliary=demo_value; Path=/; Secure
```

浏览器保存名称、值及各项属性。随后发起请求时，使用：

```http
Cookie: PASS_ID=demo_token; auxiliary=demo_value
```

两者不能直接混用：

- `Set-Cookie` 是响应头，可以出现多行；每行描述一项 Cookie 及其属性。
- `Cookie` 是请求头，其内容是要发送的名称和值。
- `Path`、`Domain`、`Expires`、`Max-Age`、`Secure`、`HttpOnly`、`SameSite` 是管理属性，不要拼成请求中的普通 Cookie。
- 不能把多行 `Set-Cookie` 合并后再按逗号拆分；`Expires` 的日期本身就含逗号（如 `Wed, 21 Oct 2026 07:28:00 GMT`）。使用成熟的 Cookie 解析器或浏览器已解析的结果。

### 2.3 LoginToken 的来源差异

在已分析的 PddWorkbench 3.7.1.18 Windows x64 样本中，所选 SDK 路径从响应头提取包含 `PASS_ID` 的 Cookie 行内容，传递到 `LoginToken` 字段时保留该字符串的属性部分。因此，该来源的字段可以是：

```text
PASS_ID=demo_token; Path=/; Secure; HttpOnly
```

浏览器获取路线读取的是已经解析的 Cookie。本文对外接入格式统一为：

```text
login_token = PASS_ID=demo_token
ck          = PASS_ID=demo_token; auxiliary=demo_value
```

原始材料和发送材料应分开处理。接收 SDK 格式时，由对应来源适配器解析并归一化；接收裸值、加密字段或其他不透明字符串时，不得自动添加前缀并当作已识别的登录凭据。

`windowsAppShopToken`、聊天 token、数据库中的加密凭据不属于上述规范化 `login_token`。不要把它们拼入 ck，也不要因为名字包含 token 就视为可互换。

## 3. 为什么 LoginToken 能用于更新 ck

在上述固定工作台样本已核对的局部路径中，`StartTokenLogin` 复制输入 `LoginToken`，将其用于登录检查和账号信息请求；相关成功分支把输入凭据存入按账号管理的本地 Cookie 记录。浏览器 Cookie 修复流程再读取该记录，解析后写回浏览器。

这说明凭据在应用内部可以沿以下方向传递：

```text
输入 LoginToken
    -> 登录检查 / 账号信息请求
    -> 按账号保存本地凭据
    -> 解析为浏览器 Cookie
    -> 后续请求携带 Cookie
```

这里的“写回”是把凭据同步到使用位置。跨项目接入不需要复制原工作台的内存结构，而应实现同样清晰的数据关系：

```text
同一会话的结构化 Cookie
    ├─ 找到唯一 PASS_ID -> 得到规范化 login_token
    └─ 按目标 URL 选择 Cookie -> 得到该 URL 的 ck
```

必须保持两个不变量：

1. `login_token` 中的 `PASS_ID` 与发送用 ck 中的 `PASS_ID` 完全一致。
2. ck 中的辅助 Cookie 来自同一次、同一个账号的会话采集，不能用新 `PASS_ID` 配旧会话的辅助项。

因此，推荐保留完整、适用的 Cookie 组合，而不是把任务简化为只更新某个 token 字符串。

## 4. 接入设计：无扩展获取架构

生产接入按三个职责边界组织：

| 模块 | 输入 | 输出 | 主要职责 |
| --- | --- | --- | --- |
| 获取模块 | 登录任务、用户授权操作 | 候选 Cookie 材料 | 管理独立浏览器、等待授权、读取 Cookie |
| 校验模块 | 候选材料、检查地址和业务目标 | 明确检查结果 | 格式检查、登录检查、账号核对、只读业务验证 |
| 业务项目 | 经验证的完整材料 | 更新后的账号凭据记录 | 并发控制、保存、使用、失效处理 |

推荐用 Playwright 管理程序自行启动的 Chromium，不依赖浏览器扩展、不连接用户日常浏览器、不读取用户日常浏览器的账号资料目录。每个账号或授权任务使用独立上下文。Playwright 提供独立上下文及相应的创建、关闭能力，见[官方上下文说明](https://playwright.dev/python/docs/browser-contexts)。

```text
业务项目发起获取任务
    |
    v
创建独立会话 / 加载属于该账号的受控会话
    |
    v
有候选材料？ -- 否 --> 打开正常登录页面，等待用户授权
    |                              |
    是                             v
    +------------------------ 采集候选材料
                                   |
                                   v
                         格式与作用域检查
                                   |
                                   v
                         独立 HTTP 登录检查
                                   |
                                   v
                         核对账号与只读业务
                                   |
                                   v
                         按账号原子提交更新
                                   |
                                   v
                         关闭本次任务资源
```

无扩展不等于无浏览器。浏览器获取模块仍需要浏览器程序及对应系统依赖；HTTP 业务模块不必在每次业务请求时启动浏览器。

## 5. 接入设计：有登录态与未登录的处理

### 5.1 已有会话

已有会话是指当前任务有权使用、且明确属于目标账号的受控会话，不是扫描机器上的所有浏览器找凭据。

1. 从该会话读取检查 URL 适用的 Cookie。
2. 检查凭据格式并执行登录检查。
3. 登录有效后，继续核对账号与业务权限。
4. 全部通过后交付本次获取结果。
5. 服务端明确拒绝时，进入 5.2 的重新授权流程；网络故障时报告无法判定，不当作登录成功。

### 5.2 没有会话或凭据已失效

1. 创建独立上下文，打开目标网站的正常登录入口。
2. 向发起任务的用户展示该任务的授权页面，让用户完成站点要求的扫码、验证码或确认操作。
3. 在任务截止时间内等待；允许用户取消。
4. 页面变化或出现 `PASS_ID` 仅作为开始采集的信号，不作为登录成功依据。
5. 读取候选 Cookie，执行独立登录检查，再核对账号与业务权限。
6. 成功后交付材料；失败、超时或取消时不返回成功结果，并清理资源。

若向前端展示二维码或授权画面，必须与本次任务及发起用户绑定，不能让用户 A 的任务使用用户 B 的授权结果。二维码、截图及其地址也应按敏感授权数据处理。

### 5.3 等待与重试

授权等待时间、单次网络超时、网络重试次数分别配置，不用一个无限循环代替全部控制。

- 授权等待到期：结束任务，报告超时。
- 用户取消：停止采集、检查和提交，关闭任务资源。
- 临时网络错误：在剩余总时间内做有限重试，并采用退避等待，避免连续高频请求。
- 明确拒绝登录：转入正常重新授权，不用相同失效材料无限重试。
- 页面明确要求人工操作：向用户显示待处理状态，不跳过身份确认步骤。

无头浏览器只是没有本地可见窗口，不代表用户授权步骤自动消失。部署设计必须提供用户可访问的授权交互方式。

## 6. Cookie 采集与作用域

### 6.1 从浏览器管理层读取

不要以 `document.cookie` 作为完整凭据出口。带 `HttpOnly` 属性的 Cookie 不向页面脚本开放；读取应由受控浏览器的 Cookie 管理 API 完成。

Playwright 的 URL 定向读取形式如下。这是采集操作片段，前提是调用方已经持有自己的 `context`；不是完整登录程序：

```python
CHECK_URL = "https://mms.pinduoduo.com/janus/api/checkLogin"
check_cookies = context.cookies(urls=[CHECK_URL])
```

返回记录包含名称、值、域、路径、过期时间、`httpOnly`、`secure`、`sameSite` 等字段。API 传入 URL 后，只返回适用于该 URL 的 Cookie。见[官方 Cookie API](https://playwright.dev/python/docs/api/class-browsercontext#browser-context-cookies)。

不要先收集所有站点 Cookie 再交给业务项目；只读取本次登录和业务访问需要的目标。

### 6.2 按目标 URL 选择

Cookie 的域、路径及安全属性决定其适用范围：

| 属性 | 处理要求 |
| --- | --- |
| 域与 host-only 规则 | 由浏览器或标准 Cookie 管理器按域匹配，不能用任意字符串后缀匹配 |
| `path` | 按路径规则选取，不能仅因域名相同就发往所有路径 |
| `secure` | 只用于 HTTPS，不向 HTTP 降级发送 |
| `expires` | 排除已经过期的项；会话 Cookie 不自行补造固定到期日 |
| `httpOnly` | 保留元数据，不通过页面脚本导出 |
| `sameSite` 及分区信息 | 保留上下文语义，不把跨站、分区 Cookie 自动压平成通用字符串 |

本文字符串 ck 接口采用简单、明确的范围：针对指定 HTTPS 目标 URL 的非分区 Cookie 集合，且名称唯一。遇到分区 Cookie 或同名多项时，返回不支持或歧义结果，不自行猜测发送规则。需要扩展支持时，应使用能够保留这些语义的结构化接口。

检查地址与业务地址应分别选择 Cookie。例如，`/janus/api/checkLogin` 和另一个业务路径可能适用不同 Cookie 集合。业务项目必须记录 ck 对应的目标 URL，不能把检查用 ck 当成全站通用模板。

## 7. 格式校验与 ck 组装

以下是本文接入设计的输入策略，不是对所有网站 Cookie 格式的统一规定。

### 7.1 输入校验规则

1. `PASS_ID` 必须存在且唯一，其值不能为空。
2. 规范化 `login_token` 必须是 `PASS_ID=值`，不携带 `Set-Cookie:` 或 `Cookie:` 前缀，不包含属性部分。
3. 凭据与请求头使用明确的 ASCII 表示；拒绝控制字符、换行、DEL 及非 ASCII 字节，不能通过忽略非法字符完成转换。
4. Cookie 名使用合法 HTTP token 字符；值拒绝空格、双引号、反斜杠和分号，这些字符会破坏本接口的字符串表示。
5. `PASS_ID` 值额外拒绝逗号。辅助 Cookie 的逗号原样保留，不把辅助 Cookie 按逗号拆开。
6. 每个 Cookie 对仅按第一个 `=` 分隔名称和值，保留值中后续的 `=`。
7. 对同一目标 URL 出现重复名称时，返回歧义错误，不采用“后一个覆盖前一个”。
8. 对规范化 token 和最终 ck 设置长度上限，例如分别为 65,536 字节。该值是本地防护配置，不是服务端规定的长度；还应遵守实际 HTTP 客户端的限制。

Cookie 名允许的字符集合可用以下正则表示：

```text
[!#$%&'*+\-.^_`|~0-9A-Za-z]+
```

### 7.2 组装步骤

```text
输入：对某个目标 URL 选出的结构化 Cookie 列表

逐项检查名称、值、作用域与过期状态
拒绝重复名称及不支持的 Cookie 语义
查找精确名称 PASS_ID，要求恰好一项
login_token = "PASS_ID=" + PASS_ID 的原始值
ck = 按采集顺序用 "; " 连接每项的 "名称=值"
复核 ck 中 PASS_ID 与 login_token 完全相同
输出：规范化 login_token、ck、目标 URL、结构化来源信息
```

保留原始值，不额外做 URL 编码、URL 解码、Base64、MD5 或 AES 转换。若原值含 `%xx` 或 `=`，它们仍然是该值的一部分。

采集、检查和返回应使用同一份冻结的候选材料。后台页面若改变 Cookie，应重新采集并重新检查，不能检查旧材料后返回新材料。

一次采集覆盖检查 URL、账号信息查询 URL 和各业务 URL，各组中的 `PASS_ID` 必须相同。不能在检查阶段使用一个会话，再在业务阶段从另一个上下文补取 Cookie。

## 8. 独立登录检查协议

### 8.1 请求

已核对的登录检查目标为：

```http
GET /janus/api/checkLogin HTTP/1.1
Host: mms.pinduoduo.com
Cookie: PASS_ID=demo_token; auxiliary=demo_value
```

完整地址：`https://mms.pinduoduo.com/janus/api/checkLogin`。

该请求用于检查登录状态。目标和判定规则来自固定样本分析及既有会话请求验证，不属于公开接口的长期兼容承诺；集成时应将其封装在独立的站点适配层。

“独立检查”指使用独立 HTTP 客户端，显式携带本次候选 ck，而不是只根据浏览器页面判断。HTTP 客户端不能混入其他会话的 CookieJar，也不能让库自动覆盖或追加另一份 `Cookie` 头。

传输要求：启用 TLS 证书验证；配置超时及响应大小限制；不自动跟随重定向；日志不记录请求凭据或原始响应正文。

### 8.2 响应判定

明确成功的正文形状为：

```json
{"success": true, "result": {"login": true}}
```

明确拒绝的正文形状为：

```json
{"success": true, "result": {"login": false}}
```

判定顺序如下：

| 条件 | 结果 | 解释 |
| --- | --- | --- |
| HTTP 200，JSON 对象，`success` 为布尔 true，`result.login` 为布尔 true | `verified` | 本次候选材料通过登录检查 |
| HTTP 200，JSON 对象，`success` 为布尔 true，`result.login` 为布尔 false | `rejected` | 本次候选材料被明确判定未登录 |
| 其他情况 | `indeterminate` | 无法根据本次响应确定登录是否有效 |

必须判断布尔值类型。字符串 `"true"`、数字 `1`、非空对象以及 `success=true` 但缺少 `result.login`，都不能算成功。

以下情况统一进入 `indeterminate`：连接或 TLS 失败、超时、HTTP 非 200、重定向、正文超限、非 JSON、非对象、字段缺失、字段类型错误，以及 `success=false`。

重定向不能携带原凭据继续跟随。记录固定错误类型即可；若需排查目标变化，在不携带凭据的受控诊断流程中进行，不能直接把 `Location` 原文写入普通日志。

### 8.3 三个不同的成功条件

```text
登录检查通过
    != 已确认是预期账号
    != 已确认可以执行目标业务
```

更新前必须利用目标项目认可的账号信息来源核对稳定的账号或店铺标识，不能只比对可重复的显示名称，也不能从不透明 token 中猜账号。

随后用对应业务 URL 的 Cookie 组合执行一个无写入副作用的业务请求，确认权限和返回内容符合预期。若该业务还需要独立的请求签名、CSRF 材料或其他应用令牌，由业务适配层按其协议提供，不能把登录检查通过当作已经具备这些材料。

## 9. 接入设计：跨项目交接的数据

以下为语言无关的交接约定，不限定 Python、Java、Go 或其他语言，也不定义必须部署的 HTTP 服务。

### 9.1 调用输入

| 字段 | 用途 |
| --- | --- |
| `request_id` | 标识本次获取任务，供取消、状态查询和脱敏排障使用 |
| `expected_account_id` | 期望更新的稳定账号标识；新绑定场景需由调用项目完成用户确认 |
| `target_urls` | 本次允许使用凭据的业务目标 URL 白名单 |
| `deadline` | 整个任务的截止时间 |
| 取消信号 | 允许用户或调用项目停止尚未提交的任务 |

登录检查 URL 和账号信息查询 URL 由站点适配层固定，不由调用方传入。目标 URL 不能由不受信任的输入任意指定；调用模块应固定或校验主机与协议白名单，避免将 Cookie 发往错误主机。

### 9.2 成功输出

| 字段 | 内容与约束 |
| --- | --- |
| `request_id` | 与输入任务一致 |
| `account_id` | 通过受信任账号信息来源核对的标识 |
| `login_token` | 规范化的 `PASS_ID=值` |
| `cookies` | 同次采集的结构化 Cookie，保留必要作用域元数据 |
| `cookie_headers` | 目标 URL 与该 URL 的 ck 的对应关系；单目标项目可只保留一项 |
| `checked_at` | 本次检查完成时间，使用明确 UTC 时间格式；不是到期时间 |
| `check_verdict` | 成功交接时固定为 `verified` |
| `source` | 凭据来自正常新登录或受控已有会话等来源标记 |

不要把完整业务 URL 查询参数、Cookie 值或 LoginToken 用作任务编号、日志关联键或缓存键。

原有项目若只接收一个 ck 字符串，可在接入边界选出其业务 URL 对应的那一项，但内部仍应维护账号归属、目标范围和检查时间，避免丢失更新依据。

### 9.3 状态交接

任务状态与登录检查结果分别表达。下表是接入设计中的业务状态，不是站点返回的状态码：

| 状态 | 含义 | 是否交付可用凭据 |
| --- | --- | --- |
| `authorization_required` | 需要用户开始或重新进行授权 | 否 |
| `waiting_user` | 正在等待用户操作 | 否 |
| `checking` | 正在检查候选材料 | 否 |
| `completed` | 检查、账号核对和本次任务约定的交付已完成 | 是 |
| `rejected` | 登录材料被明确拒绝 | 否 |
| `indeterminate` | 无法判断登录有效性 | 否 |
| `failed` | 格式错误、账号不符、业务验证失败等 | 否 |
| `timeout` | 任务超过截止时间 | 否 |
| `cancelled` | 提交前被取消 | 否 |

其中 `rejected`、`indeterminate` 与 8.2 的检查结论同名，表示任务因该结论而终止；检查结论本身仍通过 `check_verdict` 等字段单独表达。

失败结果只返回固定错误类型和脱敏元数据，不把候选凭据作为“失败调试信息”交出。若获取服务仅负责交付、业务项目另行保存，应分别记录“获取完成”与“保存完成”，不能提前宣称 ck 已更新。

## 10. 接入设计：可靠替换旧 ck

### 10.1 更新顺序

```text
取得候选材料
    -> 格式检查通过
    -> 登录检查 verified
    -> 账号标识匹配
    -> 目标业务只读验证通过
    -> 检查任务未取消、未超时且版本未过时
    -> 原子替换该账号的整组材料
    -> 提交成功后通知业务模块采用新版本
```

“原子替换”是指整组一起成功或一起失败，不让其他请求读到一半新、一半旧的数据。需要一起更新的内容包括 `login_token`、Cookie 集合、派生 ck、账号归属及版本信息。

### 10.2 同一账号的并发

可按账号串行处理更新；需要并发时，使用任务代次和数据库版本检查，拒绝已经被更新任务取代的结果。不能仅凭哪个请求后完成，就认定它的凭据更新。

例如，任务 A 先开始，任务 B 后开始；若 B 已取代 A，A 即使最后返回 `verified` 也不能覆盖 B。所有校验结束后、真正提交前，还应再次检查任务是否仍拥有更新资格。

### 10.3 失败时的旧记录

- 候选材料失败：不覆盖旧记录。
- 旧材料已明确被拒绝：标记为不可用，停止继续当作有效凭据发送。
- 仅发生网络错误：标记最近检查无法判定，不把错误等同于已失效，也不宣称旧材料仍有效。
- 新材料保存失败：报告保存失败，不能把获取成功当作更新完成。
- 新会话建立后：服务端可能已使旧会话失效。不能因为旧记录仍在就自动回退使用；回退前同样要重新检查。

检查时间只记录过去一次观察。后续业务请求仍需识别会话失效、权限变化和网络故障，不能把一次 `verified` 当成永久有效。

## 11. 接入设计伪代码

以下伪代码展示顺序和责任划分。`站点正常授权`、`账号查询`、`业务验证` 是由目标项目实现的适配步骤，不是可直接调用的库函数。

```text
获取并更新账号凭据(任务):
    校验任务归属、目标 URL 白名单和截止时间
    取得该账号的更新资格与任务代次

    尝试:
        创建独立的受控浏览器上下文
        若任务指定复用会话:
            仅加载该账号的受控会话

        若没有候选登录材料:
            通知需要授权
            执行站点正常授权，并有界等待用户操作

        对检查 URL、账号查询 URL 和各业务 URL 采集同次 Cookie 材料
        冻结候选材料
        校验格式、作用域、唯一 PASS_ID 和 token 一致性

        检查结果 = 独立 HTTP 检查(检查 URL 的 ck)
        若结果为 rejected 且来自复用会话:
            在截止时间内转入站点正常授权，重新采集并检查
        若结果不是 verified:
            返回拒绝或无法判定，不替换旧记录

        账号信息 = 用候选材料执行账号查询
        若账号与任务不符:
            返回账号不符，不替换旧记录

        用各业务 URL 对应的 ck 完成约定的只读业务验证
        再次检查取消、超时与任务代次
        原子提交本次整组材料
        返回不含明文凭据的更新状态

    最终:
        关闭已创建的任务页面与上下文
        释放更新资格和任务资源
```

如果获取模块与业务项目分属两个进程，材料交付发生在原子提交之前，必须经过已认证且加密的通道。真正保存凭据的项目负责提交结果；对外状态接口不返回 Cookie 明文。

## 12. 保密与部署要求

### 12.1 敏感数据边界

`login_token`、ck、结构化 Cookie、认证状态文件以及登录二维码数据都属于敏感材料。它们不应进入源代码、普通日志、异常文本、命令行参数、截图报告或持续集成构建产物。

默认在内存中交接。确需持久化时，由业务项目负责访问控制、加密存储、密钥管理、备份保护、删除及失效策略。Playwright 的认证状态文件也可能包含可用于代表账号执行操作的数据，见[官方认证状态说明](https://playwright.dev/python/docs/auth)。

普通日志保留任务编号、阶段、耗时、固定错误码、HTTP 状态码等元数据即可；不要直接记录浏览器异常、服务器正文或请求对象，因为其中可能包含凭据。

### 12.2 浏览器资源

浏览器获取模块使用专用运行身份和独立会话，不共享用户日常浏览器资料。限制并发上下文数量和单任务资源占用，在成功、失败、超时和取消路径中都执行清理。

浏览器运行文件及系统依赖随选定 Playwright 版本部署并验证，不能只安装语言库。依赖管理方法见[官方浏览器部署说明](https://playwright.dev/python/docs/browsers)。

生产故障不能靠关闭 TLS 校验或取消账号隔离来解决。认证代理、网络出口和授权展示端应纳入同一个受控部署范围。

## 13. 验收清单

下表用于目标项目验收接入实现，不是功能完成记录。

| 场景 | 应满足的结果 |
| --- | --- |
| 从空会话开始 | 用户正常授权后才获得材料，全程不依赖扩展或用户日常浏览器 |
| 复用受控会话 | 先检查再使用，不凭 Cookie 存在直接返回成功 |
| 候选材料有效 | 明确 `verified`，账号匹配且只读业务通过后才交付或提交 |
| 无 PASS_ID、空值、重复名称 | 返回对应失败，不猜值、不覆盖旧记录 |
| token 与 ck 不一致 | 拒绝整个候选结果 |
| 含请求头注入字符 | 拒绝输入，不发出请求 |
| 值含 `=`、辅助值含逗号 | 按本规范保留值，不错误拆分或转码 |
| Cookie 域、路径、过期不匹配 | 不向目标发送不适用项 |
| 检查返回 false | 明确拒绝，并引导正常重新授权 |
| 非 200、重定向、非法 JSON、类型错误、网络超时 | 无法判定，不误报成功或明确失效 |
| 用户登录了其他账号 | 不更新原目标账号的记录 |
| 同账号并发任务乱序完成 | 旧任务不能覆盖已取代它的新任务 |
| 用户取消或任务超时 | 提交前停止；释放资源；旧记录不被候选材料覆盖 |
| 数据保存失败 | 报告保存失败，不报告更新成功 |
| 普通日志及错误输出 | 不含 token、ck、认证状态和二维码敏感数据 |

判断最终交付是否达标的标准是：**业务项目能拿到属于预期账号、对指定目标可用的登录材料，并可靠替换对应 ck；失败时不混淆状态、不串账号、不泄露凭据。**
