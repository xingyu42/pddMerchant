## 一、多多客服 → 销售数据

入口：`/mms-chat/overview/service` 页内点击「销售数据」页签。页面顶部提示原文：

> 销售数据仅支持查看3天之前的数据，例如消费者当日咨询后，3日内下单订单都算作当日的询单订单

页面区块：

- 实时数据（「每小时更新」）：店铺销售额(元)、成团人数(人)
- 数据总览：统计时间默认 `2026-11-10 至 2026-11-16`（实测当天是 11-19，即近 7 天 = [今天-9, 今天-3]）；可选近 1 天 / 近 7 天 / 近 30 天 / 自定义；指标卡为询单人数(人)、最终成团人数(人)、询单转化率、客服销售额(元)、客服可提升销售额(元)，各带「较前 7 日」
- 近 30 天趋势图（可切换指标）
- 指标卡上没有找到说明浮层，各指标的官方定义只有顶部那一句提示

点击页签后页面发出的业务请求：

- `GET /api/server/_stm`
- `POST /desert/stat/mallSalesOverviewData`

### 1.1 `/desert/stat/mallSalesOverviewData`

POST `{ startDate, endDate }`（`yyyy-MM-dd`），明文，外壳 `{ success, errorCode, result }`（经签名客户端重放时 `errorCode` 为 0）。

| 字段 | 页面标签 | 样例（11-10~11-16） | 单位 |
| --- | --- | --- | --- |
| `inquiryOrderUserCnt` | 询单人数 | 12 | 人 |
| `groupUserCnt` | 最终成团人数 | 6 | 人 |
| `inquiryOrderTransformRate` | 询单转化率 | 0.5（页面 50.00%） | **0-1** |
| `csSalesAmount` | 客服销售额(元) | 153.67（页面 153.67） | **元** |
| `csCanImproveSalesAmount` | 客服可提升销售额(元) | 23.14 | 元 |
| `*Compare` | 较前 N 日 | 页面默认区间为 0，其余区间为 `null` | 0-1（推断） |

区间重放（实测当天 11-19）：

| 请求区间 | 询单 / 成团 / 转化率 / 客服销售额 | 说明 |
| --- | --- | --- |
| 11-18 ~ 11-18 | 全部 `null` | 落在 3 天延迟内 |
| 11-19 ~ 11-19 | 全部 `null` | 今天 |
| 11-12 ~ 11-18 | 5 / 1 / 0.2 / 17.78 | 与逐日 11-12~11-15 之和一致 |
| 11-12 ~ 11-19 | 5 / 1 / 0.2 / 17.78 | 结束日取今天也不报错 |
| 10-20 ~ 11-18 | 40 / 21 / 0.525 / 449.58 | 与逐日之和一致 |
| 09-17 ~ 11-18（63 天） | 54 / 26 / 0.4815 / 554.26 | |
| 09-16 ~ 11-18（64 天） | 同上 | 超过 63 天不报错 |
| 08-21 ~ 11-18（90 天） | 同上 | 同上；更早的数据是没有保留还是本来没有询单，无法区分 |

结论：

- 结束日落在延迟期内不会报错，上游只汇总已出数的日期。命令如果沿用「截至昨天」的窗口，标出的区间会比实际统计的区间多出最后两三天
- 区间汇总的询单人数、成团人数、客服销售额在上面三个区间都等于逐日之和（12、5、40）。没有观察到跨日去重；本店询单量很小，这一点不足以推广
- 区间上限：64 天和 90 天的请求都成功返回。页面「自定义」日期控件的可选范围本次没有读取

### 1.2 `/desert/stat/mallMonthSalesData`

GET，无参数，明文，`result` 为 31 行的逐日数组，本次为 10-17 ~ 11-16（[今天-33, 今天-3]）。

## 三、对接入方案的影响

- 客服销售数据的窗口要以今天-3 为结束日，或者在区块里单独标出实际统计区间
- 客服销售额成团为 0 时是 `null`；转化率在询单 0 人时上游已经给 `null`
- 同类目询单转化率均值只能放在逐日趋势里
- 商品评价评分区块：页面只展示评价数和排名；三项均分是页面没有展示的字段，含义来自字段名和一次交叉核对
- 商品列表分页只确认了每页 10 条
